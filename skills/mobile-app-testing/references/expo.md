# Expo iteration and OTA verification

Use Expo's maintained tools and documentation as the interface. Inspect the project's package manager, SDK, app config and EAS profiles, then installed CLI versions, command help and available tool schemas. Use a compatible CLI through that package manager; upgrade only when needed within task permissions. Do not copy another run's shell loops, API payloads, session IDs or account availability into a reusable automation layer.

Read the [EAS CLI reference](https://docs.expo.dev/eas/cli/) and [official EAS simulator skill](https://github.com/expo/skills/blob/main/plugins/expo/skills/eas-simulator/SKILL.md), including its relevant run/controller references, before using cloud simulators. They document current commands and data flow; they do not authorize paid capacity, feedback submission, installs, tunnels or other actions beyond this task. Preserve user permissions and this run's ownership rules if a documentation example resets shared state or leaves a resource running.

## Choose the loop

- **Edit and reload:** reuse a development client with compatible native modules, SDK and fingerprint; verify it is actually a dev client. Connect it to the intended worktree's Metro server and prove a current-source change renders. A static release binary cannot use Fast Refresh. Use official Expo start and agent-device Metro operations where supported. Reuse an authorized compatible Metro instance with known ownership; otherwise start one owned server on a free port. A remote device needs a reachable Metro endpoint; follow the current documented tunnel data flow and existing task authorization, recording the endpoint privately. Diagnose transport separately from app failure.
- **Native change or missing compatible client:** check existing matching build jobs/artifacts before building. Changes to native dependencies, SDK, plugins or native configuration need a compatible new binary. Use the project's explicit development-client profile and official build tooling. Rebuild for those changes or the required final candidate, not ordinary JS edits or a tunnel failure.
- **OTA/release behavior:** use an update-enabled internal QA binary to test installed update loading, offline operation and rollback. A Metro result is development evidence; it does not establish production-like update behavior. Reuse a compatible QA binary for JS/assets updates and retain its identity alongside the running update identity.

When OTA compatibility unexpectedly changes, use official `eas fingerprint:compare` with the actual build and intended environment to identify the changed inputs. Build configuration such as `eas.json` can affect the fingerprint even when the UI change is JavaScript-only. Do not force a runtime value or promise reuse from the UI diff alone; resolve the configuration or deliver a matching binary, then verify its identity.

## iOS artifact and delivery checks

Hosted iOS Maestro needs a simulator build; a signed store IPA intended for TestFlight cannot run there. When TestFlight delivery is in scope, build the simulator and store artifacts from the same accepted app source with the intended backend and update channel. Use existing EAS-managed signing/submission credentials when available; a reachable Mac or another Apple login is not required for hosted builds and tests. Check the installed CLI and [iOS submission contract](https://docs.expo.dev/submit/ios/) before acting.

Keep simulator acceptance, store upload, Apple processing and tester availability as separate results. Reconcile the exact submitted store build in App Store Connect; a finished EAS submission alone does not establish TestFlight availability. A passing simulator flow does not prove a physical iPhone installation. Resolve actual signing, processing or export-declaration requirements from the app and existing account evidence; never invent answers just to clear a release gate.

## Official cloud simulator gate

Before any session creation, verify the intended Expo account/project and run the current CLI's read-only `simulator:availability --json`. Record timestamp, account, CLI version and sanitized response in the project/run evidence. Availability is an account/provider fact that must be checked afresh; never hardcode a project's last result into this skill.

If `available` is false, do not call start. Report the provider's returned waitlist/service URL and select an appropriate existing local device or authorized fallback. Opening that URL in the user's browser does not enable access; repository configuration cannot change the provider gate. An unknown command means the installed CLI lacks that interface, not proof that the account is disabled: consult current help/docs or a permitted compatible version. Authentication failure is likewise distinct from availability.

When available and authorized, use EAS `simulator:*` for session lifecycle and agent-device through the documented `simulator:exec` interface for interaction. Check current help/schema for flags, JSON output and connection-state behavior; do not invent simulator tap/install commands. Confirm readiness from provider state before install/drive. A viewer link is for the user's browser, never an app deep link or an instruction to stop testing.

Checkpoint a human-readable purpose plus per-run unique ownership name/ID before start, the authorized lifetime/deadline and cleanup owner. Apply the provider-enforced duration when supported; verify the returned expiry fits the budget, otherwise use a bounded manual deadline or another permitted runtime. Reconcile an interrupted request by exact owned session identity before retrying. A stale dotenv is not proof of a live session. Keep `.env.eas-simulator` and remote connection tokens private and untracked; never overwrite or clear another run's state. JSON mode may change whether the CLI writes connection state: follow the current contract.

After the run, save evidence, stop the exact owned session and Metro/tunnel processes, verify provider termination, then clear only owned stale session state. A requested live preview may remain only for its agreed bounded duration with an explicit cleanup owner. Do not treat a shell timer as guaranteed provider shutdown.

## Plan benefits and optional hosted testing

Check [official pricing](https://expo.dev/pricing) and the [simulator service page](https://expo.dev/services/simulators) when discussing a subscription. Build priority/credits, update allowances and workflow entitlements are separate from interactive cloud simulator availability. Do not promise that Starter or another paid plan unlocks simulator access: confirm current terms and the live account availability response. A plan change is not a repair for a failed access gate.

For unattended recurring regression, prefer authorized managed cloud CI when a personal Mac may be off. Use the optional [EAS Workflows Maestro job](https://docs.expo.dev/eas/workflows/pre-packaged-jobs/#maestro). The EAS-hosted job is `type: maestro`; `type: maestro-cloud` invokes the separate external Maestro Cloud service and requires its own account/subscription. Neither is the interactive EAS Simulator service. Check current plan support, job schema, compatible build inputs and job/compute usage charges before an authorized run. Hosted Maestro executes test flows and produces results; it does not grant an interactive simulator session or replace the dev-client/Metro edit loop. Reuse existing flows where suitable and record the exact tested artifact and job result.

A hosted EAS Maestro job has run on Starter while interactive EAS Simulator remained unavailable to the same account. Treat this as evidence that the capabilities have separate gates, not a lasting entitlement guarantee. Hosted regression does not require a personal Mac to stay awake. Do not claim Expo is cheaper without measured comparable usage and current terms.

Checkpoint the workflow run ID, individual job IDs, tested build and artifact locations privately before waiting for cloud completion. Reconcile remote status after interruption before launching a replacement. Check the installed CLI version and command help: in EAS CLI 23.2, `workflow:logs` takes the individual Maestro job ID, not the workflow run ID. Retrieve that job's logs and native evidence even on failure.

Validate flow structure and expressions separately. Maestro `check-syntax` and EAS workflow validation accepted `${/regex{12}$/.test(ID)}` even though Maestro interpolation failed at runtime before login. A probe using the installed Java interpreter reproduced the failure; rewriting the expression without internal braces or dollar signs worked. For similar failures, inspect interpolation and test the actual expression in the installed Maestro interpreter before another cloud run. This is not a blanket ban on regex. Static validation or an interpreter probe does not establish a native flow pass; rerun the affected device case.

In nested monorepos, an EAS `upload_artifact` path can resolve differently from the shell hook's working directory. Record an absolute evidence directory derived from the hook's `$PWD`, expose it as a step output, and pass that output to artifact upload. A relative glob lost native proof despite files existing in the hook. Verify the downloaded artifact actually contains the screenshots, video and assertion results; a successful hook alone does not prove evidence was retained.

Local devices and dev clients remain useful for interactive work or as a fallback; avoid making unattended regression depend on a personal machine staying on. Neither hosted option is required for Expo development or OTA verification. A compatible development client on an authorized phone or local emulator/simulator can connect to Metro; an update-enabled QA binary on that device can exercise the isolated OTA checks below. Preserve platform/signing requirements and device ownership when choosing this route.

## Isolated QA OTA checks

Read current [runtime compatibility](https://docs.expo.dev/eas-update/runtime-versions/), [EAS environment](https://docs.expo.dev/eas/environment-variables/) and [rollback](https://docs.expo.dev/eas-update/rollbacks/) documentation. Use the project's existing runtime policy; when establishing a new QA setup, prefer a native fingerprint policy where supported. Check evaluated platform runtime/fingerprint against the installed binary before publishing. Never force a mismatched update to load by relabeling its runtime.

Making an existing transitive native module a direct dependency at the exact same revision can preserve the fingerprint, but verify this with the official preflight for the actual project. One unchanged result is not permission to assume compatibility for other dependency edits or force the fingerprint.

Select an isolated QA channel and its actual branch mapping, explicit EAS environment, test backend/tenant and update-enabled binary. Inspect mappings before any write; an innocently named channel may still reach production. Use matching build/update environment configuration and verify resolved public endpoint identities without exposing secrets. A channel is distribution routing, not backend isolation. Configuration or publication changes require the task's existing authorization; this skill grants none. Do not change production channels or promote a QA update as part of testing.

For an authorized QA update, record source revision, platform, binary build ID/version/checksum, installed app identity, runtime/fingerprint, channel/branch/environment, update group and platform update ID. Use supported on-device diagnostics to assert which update actually runs after the documented fetch/reload/restart sequence; distinguish embedded launch, downloaded update and Metro. Preserve both the initial and final identities. A published update ID alone is not device verification.

A fresh `clearState` smoke starts from the installed baseline. Publishing a fix does not make that smoke test the fix: download and apply the exact intended platform update UUID, then assert the running UUID before the affected flow. Read the native build number through a supported installed-binary API, such as `expo-application`'s `nativeBuildVersion` on SDK 57; deprecated `Constants.platform.android.versionCode` or a mutable OTA manifest cannot establish installed-binary provenance.

When OTA behavior is in scope, exercise a bounded matrix on that QA binary:

- Online update acquisition and restart: assert the intended running update ID and changed behavior.
- Offline cold launch after download: disable native connectivity, terminate and relaunch the app, then verify the expected cached update or embedded fallback and the supported session state. Restore connectivity and verify session recovery and the intended tenant. Warm offline operation or an online restart does not establish cold offline startup/reconnect.
- Interrupted download, when in scope: independently observe `Downloading` before disabling native connectivity; confirm the download error, unchanged running update UUID and absence of `Ready`. Reconnect, retry manually and verify the exact target running UUID after apply/restart. A late network cut that already shows `Ready` does not prove interruption; retain it as an inconclusive attempt.
- Rollback/recovery: use the project's selected official rollback or known-good republish route only within QA authorization. Verify the running ID/embedded state after reconnection and restart and repeat the affected assertion. Recovery requires network when the rollback has not yet been received; report offline cached behavior separately. Backend/schema/data changes are not undone by a JS rollback.

For offline authentication, a credential/token cache does not establish that the SDK can bootstrap a session after cold launch. Inspect the installed SDK's supported resource-cache mechanism; treat experimental options as version-specific and confirm behavior natively, beyond an SDK probe. Enabling offline options can surface network errors previously muted by the SDK: audit sign-out and failure handlers, retain saved user choices until authentication confirms the transition, and preserve live tenant authorization gates. Cached session data must not substitute for current authorization to tenant operations.

Record pass/fail/blocked/not-run per case with independent assertions and native media as required by the evidence gate. If no compatible QA binary or runtime is available, preserve the Metro result as such and mark OTA checks blocked. Never infer OTA or release verification from development refresh alone.
